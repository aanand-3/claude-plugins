# P-083: The PM amends goal and item sections through the hub

## Context
FEAT-075 (G-007, P1). Under the lifecycle preset the PM's and Director's `paths.write` is `.crew/drafts/**`, and the hub
has no command that edits a goal's or item's sections; it only logs, triages, moves and re-goals. Agreed scope changes
(G-009's stale Breakdown, Q-088a6e on G-005 / FEAT-072 / FEAT-066) were logged as notes and waited for a human to edit
the files by hand (3d50d9b). This plan adds `amend`: one section of an item or goal replaced from a draft, gated by role
like `regoal` (P-055) and logged on the document and in the ledger, so the owners change what they own through the hub
without widening anyone's write paths.

Binding knowledge: K-2026-10-26-authorize-refuses-every-role-but (role gates through `authorize`, `also` widens only on a
deliberate decision), K-2026-10-23-approvals-are-human-agents-never-pass, K-2026-10-23-every-module-stays-under-300-lines
(backlog.ts is near its limit, so `amend` gets its own module), K-2026-10-25-each-command-registers-its-cli-spec-help,
K-2026-10-25-a-plan-that-adds-a-hub-command-or-mcp, K-2026-10-26-add-plugins-crew-docs-reference-md and
K-2026-10-26-since-p-025-npm-run-build-also (generated blocks in plugins/crew/docs), K-2026-10-26-goal-breakdown-lines-split-title-from.

## Scope
**In:**
- `amend ID --section NAME --from DRAFT --note TXT [--approved-by NAME] [--keep-draft]`, CLI and MCP tool `amend`
  (`id`, `section`, `from`, `note`; no approval field, as for every MCP tool). ID is a FEAT/BUG/CHORE/SPIKE item or a goal.
- The draft holds the new body of that one section. It is refused (nothing changed) when it is empty after stripping
  template comments, or when it contains a `## ` heading (one section per call, no smuggled sections) or front matter.
- Amendable sections are the document's template sections (item-<type>.md for items, goal.md for goals), except the logs:
  an item's `Notes` and a goal's `Progress log` are append-only (`log`). Front matter is never amendable: `--section`
  naming a front-matter field (status, goal, priority, severity, plan, …) or an unknown section is refused with the
  command that owns it where there is one (`move`, `triage`, `regoal`). A section missing from an older document is
  added (Doc.replaceSection's `before`).
- Effect: the section body is replaced; one line `amended <Section> by <actor>: <note>` is appended to the item's `Notes`
  or the goal's `Progress log`; one ledger `log` event on the document carries the same text (no new event type, as
  `regoal`). `--note` is required. The draft is consumed unless `--keep-draft`.
- Gates (new off-flow actions `item.amended` and `goal.amended` in `ACTIONS`, policy.ts; lifecycle preset role gates both
  to `pm`):
  - Items: the PM amends any section of an open item. The Architect may amend an item's `Acceptance criteria` while
    specing its plan: the item has no plan, or its plan is `draft` (`authorize(..., also: ["architect"])` only in that
    case, a deliberate widening recorded as a decision).
  - Goals: the PM amends `Breakdown` and `Notes & decisions` of a proposed or active goal, and any section of a proposed
    goal. On an active goal, `Outcome`, `Scope`, `Acceptance criteria` and `Success metrics` (the scope the executive
    approved) need `--approved-by NAME` in every mode and preset; without it the command fails naming the exact command
    to run with the approval.
  - Closed documents are refused: items `done`, `wontfix`, `duplicate`; goals `done`, `dropped`.
- An amended Breakdown of a goal turns its new candidate lines into FEAT items exactly as `new-goal` does
  (`breakdownToItems`, reused unchanged from backlog.ts); lines already naming an item ID stay links.
- Docs and agent text: `pm.md` (amend next to re-goal), `architect.md` (amend an item's criteria while specing),
  `model.md` (the two gates and the rule above), the gates table in `plan-lifecycle.md` and the command/tool blocks in
  `reference.md` (regenerated by `npm run build`; `diagrams.ts` gets the two action descriptions).

**Out (explicitly not doing):**
- Amending plans (the Architect edits draft plans in place), the idea, or knowledge entries.
- Any change to `paths.write`, the guard, or `.crew/policy.yaml`; the guard already lets every role call the hub.
- A Director amend right (the item names the PM and the Architect only).
- Re-rendering `.claude/agents/**` (protected; the human runs `crew.mjs agents` after landing).
- Diffs or history of amended text beyond the log line and the git history of the hub document.

## Acceptance criteria
- [ ] AC1: `amend FEAT-### --section "Acceptance criteria" --from DRAFT --note TXT` replaces only that section of the item
  (every other section and the front matter byte-identical), appends `amended Acceptance criteria by <actor>: TXT` to its
  Notes, records one ledger `log` event on the item with that text, and consumes the draft. The same works for a goal's
  Breakdown, logging to its Progress log.
- [ ] AC2: Refusals change nothing (file bytes and ledger length unchanged): missing `--note`; a front-matter field or an
  unknown section as `--section` (status/goal/priority name `move`/`triage`/`regoal`); an item's `Notes` or a goal's
  `Progress log`; an empty draft; a draft containing a `## ` heading; an ID that is not an item or goal.
- [ ] AC3: Under the lifecycle preset: the PM amends any section of an open item; the Architect amends `Acceptance
  criteria` of an item with no plan or whose plan is draft, and is refused for any other section and once the plan is
  ready or later; a developer or QA run is refused for every section. `policy show` lists `item.amended pm` and
  `goal.amended pm` (preset lifecycle).
- [ ] AC4: Goals: the PM amends `Breakdown` and `Notes & decisions` of an active goal without approval, and any section of
  a proposed goal. Amending `Outcome`, `Scope`, `Acceptance criteria` or `Success metrics` of an active goal fails without
  `--approved-by` (the message names the command with the approval flag) and succeeds with it, logging the approver.
- [ ] AC5: Closed documents are refused: an item `done`, `wontfix` or `duplicate`; a goal `done` or `dropped`.
- [ ] AC6: An amended Breakdown of an active goal with a new candidate line creates one FEAT item linked to the goal and
  rewrites the line to `FEAT-###: …`; existing `FEAT-###` lines are unchanged and create nothing.
- [ ] AC7: The guard allows a PM agent's `node .crew/bin/crew.mjs amend …` (identity injected, not refused) while the PM's
  effective `paths.write` stays `.crew/drafts/**`; run from a plan worktree, the amend writes the main checkout's hub
  document, and no copy under the worktree's `.crew/` changes.
- [ ] AC8: The MCP tool `amend` is listed and works as AC1; generated docs are current (`test/docs.test.ts`), and the
  command registry checks pass (`test/hub/registry.test.ts`, `test/mcp.test.ts`).

## Approach
- New module `packages/crew/src/hub/commands/work/amend.ts` (well under 300 lines) with `amend(store, id, o)` and
  `amend.reg.ts` (CLI spec, usage line, MCP tool), listed in `commands/index.ts`. backlog.ts is not touched: it is close
  to the line limit and in P-073/P-074.
- Order of checks, all before any write: document kind → closed → section allowed for the kind/type (template sections
  minus the log section; front-matter names get the owning command in the message) → `--note` → draft read via
  `store.readDraft(path, "section")` and validated → gate. Gate: `authorize(store, id, "<kind>.amended", approvedBy,
  undefined, cmd, also)` where `also` is `["architect"]` only for an item's Acceptance criteria with no plan or a draft
  plan; then, for an active goal's Outcome/Scope/Acceptance criteria/Success metrics, a missing `approvedBy` fails with
  `crew.mjs amend G-### --section "…" --from … --note … --approved-by <name>`.
- Write: `doc.replaceSection(section, body)` (doc.ts, existing; `before` = the log section for missing sections),
  `appendLog(text, logSection)`, `save()`, `store.ledger.record("log", id, { text })`; text includes `(approved by NAME)`
  when given. For a goal's Breakdown, `breakdownToItems(store, goal)` after save. Then `store.consume(draftFile, keep)`.
- Hub documents resolve through the Store, which already writes the main checkout from any worktree (as `regoal`).
- `ACTIONS` gains `item.amended`, `goal.amended`; lifecycle `role_gates` gains both → `pm`; `diagrams.ts` gets their
  descriptions so the plan-lifecycle gates table regenerates.
